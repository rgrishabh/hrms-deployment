# Deployment guide

**One customer = one independent installation.** Every installation has its own database, secrets, storage, domain, branding and modules, and runs without contacting any other installation or a central service. There is no signup page, onboarding portal or tenant switching: customers are provisioned by deploying an installation.

Two supported paths, with the same configuration names and meaning:

| | Docker Compose on a VM | Terraform on AWS |
|---|---|---|
| Where | `deploy/compose/` (one copy per customer) | `infra/` (one AWS account per customer) |
| Customer settings | `.env` | `terraform/customers/<slug>.tfvars` |
| Secrets | `.env` (mode 600), generated by `bin/init-env` | AWS Secrets Manager (generated by Terraform) |
| Database | `postgres:17` container + named volume, private network | RDS PostgreSQL (Multi-AZ, KMS, TLS enforced) |
| HTTPS | Bundled Caddy (Let's Encrypt) or your proxy | ALB + ACM certificate + WAF |
| First admin | One-time setup link | Temporary password in Secrets Manager, changed at first sign-in |
| Verified here | `docker compose config` with a full customer config; the full command sequence rehearsed with the resolved environment (see TESTING.md). **Not run in a Docker engine yet** (none available) | `terraform validate` + offline module tests. **Never applied to AWS yet** |

## 1. New customer with Docker Compose

Requirements: a Linux VM with Docker Engine and the Compose plugin, a DNS name pointing to it, and outbound internet for image pulls and Let's Encrypt.

```bash
# On your workstation: build and publish the image once per release (the same image serves every customer)
docker build -f apps/api/Dockerfile -t registry.example.com/labhrms:1.0.0 .
docker push registry.example.com/labhrms:1.0.0

# On the customer's VM: one directory per customer
sudo mkdir -p /opt/hrms/customer-a && sudo chown "$USER" /opt/hrms/customer-a
cp -R deploy/compose/. /opt/hrms/customer-a/          # compose.yaml, Caddyfile, bin/, branding/, .env.example
cd /opt/hrms/customer-a
cp .env.example .env
bin/init-env                                          # fills the 4 secrets with strong random values, chmod 600
"${EDITOR:-vi}" .env                                  # replace every <placeholder>; see section 3
cp /path/to/customer-a-logo.svg branding/logo.svg     # optional, then BRAND_LOGO_URL=/branding/logo.svg

docker compose up -d                                  # db -> provision -> migrate -> app
docker compose --profile tools run --rm bootstrap     # prints the one-time administrator setup link
docker compose --profile https up -d                  # optional: automatic HTTPS with Caddy
docker compose ps                                     # app becomes "healthy" once bootstrapped
```

Give the setup link to the customer's administrator through a secure channel. It works **once** and expires in 24 hours. They open it, choose a password, sign in, and configure the organization (legal entities, branches, departments, employees, shifts, policies) inside the HRMS.

A second customer on another VM uses another copy with its own `.env`. On the **same** VM, use a different directory, `COMPOSE_PROJECT_NAME` and `APP_PORT`, and one shared reverse proxy, because two Caddy containers can't both bind ports 80 and 443. Separate VMs are recommended.

What isolates installations: a separate Compose project, which means separate containers, networks and the `db-data` volume. Each has its own database credentials and encryption key. The database publishes no port, and the `internal` network has no route out of the host. The app is bound to `127.0.0.1` unless you change `APP_BIND_ADDRESS`.

## 2. New customer with Terraform (AWS)

Full runbook: **[infra/README.md](infra/README.md)**. In short:

```bash
cp terraform/customers/_template.tfvars       terraform/customers/customer-a.tfvars      # non-secret settings
cp terraform/customers/_template.backend.hcl  terraform/customers/customer-a.backend.hcl # state location
# add {"slug":"customer-a","account_id":"…","region":"ap-south-1","canary":false} to environments/prod/customers.json
cd terraform/envs/customer
terraform init -reconfigure -backend-config=../../customers/customer-a.backend.hcl
terraform plan  -var-file=../../customers/customer-a.tfvars
terraform apply -var-file=../../customers/customer-a.tfvars   # first apply by an administrator; later via pipeline
```

Then run the **Release** workflow. In that account it runs provision → migrate → **bootstrap** (creates the organization and the first administrator) → starts the service.

Hand-over: an operator reads the secret `hrms/bootstrap-admin` (the read is logged in CloudTrail) and gives it to the customer's administrator securely. They must change it at first sign-in.

## 3. Branding and organization identity

Set at deployment level and **read-only in the app**. Admins see them under Settings → Installation.

| Compose `.env` | Terraform | Meaning |
|---|---|---|
| `PRODUCT_NAME` | `branding.product_name` | Product name (page title, footer) |
| `BRAND_NAME`, `BRAND_SHORT_NAME` | `branding.brand_name`, `short_name` | Customer brand (login, sidebar, title) |
| `BRAND_LOGO_URL`, `BRAND_FAVICON_URL` | `branding.logo_url`, `favicon_url` | `https://…` or `/branding/<file>` (Compose only). Initials are shown if absent |
| `BRAND_PRIMARY_COLOR`, `…SECONDARY…`, `…ACCENT…` | `branding.*_color` | Hex colours. **Quote them in `.env`**: `"#14532D"` |
| `BRAND_LOGIN_MESSAGE`, `BRAND_SUPPORT_EMAIL`, `BRAND_SUPPORT_PHONE`, `BRAND_HELP_URL` | `branding.*` | Login text and help contacts |
| `ORGANIZATION_NAME`, `ORGANIZATION_LEGAL_NAME` | `organization.name`, `legal_name` | Organization identity |
| `ORGANIZATION_COUNTRY`, `ORGANIZATION_CURRENCY` | `organization.country`, `currency` | `IN`, `INR` |
| `ORGANIZATION_TIMEZONE`, `ORGANIZATION_DATE_FORMAT` | `organization.timezone`, `date_format` | Installation defaults. Admins may override them as business settings |
| `ORGANIZATION_FY_START_MONTH` | `organization.fy_start_month` | Financial year start (4 = April) |

To change any of these: edit `.env`, then run `docker compose up -d` (recreates the app). On AWS, edit the tfvars, apply, then release. No rebuild: the same image renders any branding at runtime, through `GET /api/v1/public/config` and an `index.html` rendered at startup.

Not yet branded, because the features don't exist yet: emails, payslips and other PDFs, and exports. They will take branding from the same configuration.

## 4. Domains and HTTPS

- **Domains:** `APP_URL` (primary) and `APP_EXTRA_DOMAINS` (Compose), or `domains` (Terraform). The application answers **only** these hostnames, and anything else gets 404. They are synced into the database at startup and by bootstrap. Changing them needs only a restart.
- **Compose HTTPS:** point DNS at the VM, set `CADDY_SITE_ADDRESSES`, then run `docker compose --profile https up -d`. Or use your own proxy to `127.0.0.1:${APP_PORT}`. The proxy must preserve the `Host` header and set `X-Forwarded-For`, with `TRUST_PROXY=true`. Plain HTTP isn't supported in production, because cookies are `Secure`.
- **AWS HTTPS:** an ACM certificate on the ALB. With `route53_zone_id` it's fully automatic. Otherwise the customer adds the validation records and a CNAME from the Terraform outputs (two-step apply in infra/README.md).

## 5. Initial administrator

There's no HTTP signup or bootstrap endpoint. Bootstrap is a command that needs database-owner credentials.

| | Compose | AWS |
|---|---|---|
| Command | `docker compose --profile tools run --rm bootstrap` | Runs automatically in every release (`hrms-ops` task) |
| Credential | **One-time setup link** (`/setup#token=…`): single use, 24 h, stored hashed, in the URL fragment so it never reaches server logs | **Temporary password** from Secrets Manager (`BOOTSTRAP_MODE=password`); **must be changed at first sign-in** |
| Re-run | Safe: never creates a second organization or administrator; prints nothing if an admin exists | Same |

**Recover administrator access** (lost password, admin locked out, admin role removed):
```bash
docker compose --profile tools run --rm bootstrap --reset-admin --admin-email it@customer-a.example.com
```
This invalidates the old password and all sessions, unlocks the account, restores the Administrator role, and prints a new one-time link. On AWS, run the `hrms-ops` task with command `node dist/src/db/bootstrap.js --reset-admin --admin-email <email>` and `BOOTSTRAP_ADMIN_PASSWORD` set from a fresh secret value; the user is forced to change it. Every bootstrap run is recorded in the audit log.

## 6. Database and storage

- **Compose:** the `db` service (`postgres:17-alpine`), with data in the `db-data` volume. It's on a private network, and no port is published. Roles: `hrms_owner` owns the schema (migrations, bootstrap, backups); `hrms_app` is the runtime role (no superuser, no BYPASSRLS). The app refuses to start otherwise. `provision` creates both on every `up`.
- **AWS:** RDS PostgreSQL 17. Connections use `DATABASE_SSL=verify-full` with the RDS CA bundle in the image.
- **Storage:** documents live in the installation's own `app-storage` volume (Compose) or private S3 bucket (AWS). See docs/DOCUMENTS.md. `bin/backup` / `bin/restore` cover the database **and** the documents.

## 7. Optional modules

`ENABLED_MODULES` (Compose) or `enabled_modules` (Terraform). `default` means core HR plus web attendance, regularization, shifts, holidays, **leave** and self-service. Add `attendance.mobile`, `attendance.biometric` `expenses` (needs storage, docs/EXPENSES.md), `training` and `lab.competency` (docs/COMPETENCY.md), `core.policies` (docs/POLICIES.md) and/or `notifications.email` (needs `MAIL_TRANSPORT=smtp` and `SMTP_*`; see docs/NOTIFICATIONS.md).

- Validated at startup. Unknown modules, modules not available in this release (payroll, expenses, …), or missing dependencies stop the process with a clear error.
- A disabled module is hidden in the UI and its API returns `403 feature_unavailable`. Device ingestion for a disabled biometric module is refused too.
- **Changing modules needs a restart** (`docker compose up -d`, or a release). **No data is deleted** when a module is disabled, and enabling it again shows the existing data.
- Configured-but-not-ready modules report it. For example, biometric is "configuration incomplete" until the first device is registered.

### Two-factor authentication
`MFA_ENFORCEMENT` (default `privileged`): administrators, HR administrators, payroll managers and IT administrators must set up an authenticator app at their next sign-in. `all` requires it for everyone; organizations can make it stricter under Settings → Security, never weaker. A lost phone: the user signs in with a recovery code, or an administrator uses **Users → Reset two-factor authentication**. For the first administrator, `bootstrap --reset-admin` also clears it.

### Background jobs
Run inside the app (no extra service): nightly attendance close, monthly leave accrual, session cleanup. Safe with several app instances. `JOBS_ENABLED=false` turns the scheduler off for an instance. History and Run now: Settings → Scheduled jobs.

## 8. Secrets

| Secret | Compose | AWS |
|---|---|---|
| Postgres superuser | `POSTGRES_SUPERUSER_PASSWORD` (only `db` and `provision` receive it) | RDS-managed master secret (only the `hrms-dbadmin` task) |
| Owner / app DB passwords | `DB_OWNER_PASSWORD`, `DB_APP_PASSWORD` | `hrms/database-migration-url`, `hrms/database-url`, `hrms/db-*-password` |
| Field encryption key | `DATA_ENCRYPTION_KEY` (32 bytes, base64) | `hrms/data-encryption-key` |
| First admin | n/a (setup link) | `hrms/bootstrap-admin` |
| SMTP password (if email is used) | `SMTP_PASSWORD` | `hrms/smtp-password` (set by an operator; see docs/NOTIFICATIONS.md) |

Secrets are never in the image, never exposed to the browser (the public config contains no secrets, and a test checks this), and never logged. **Terraform state contains the generated passwords**, which is why the state bucket is KMS-encrypted and access-restricted per account. Never reuse secrets across customers. `bin/init-env` generates new ones per installation.

## 9. Upgrades

**Compose**
```bash
bin/backup                                    # always back up first
sed -i 's#^HRMS_IMAGE=.*#HRMS_IMAGE=registry.example.com/labhrms:1.1.0#' .env
docker compose pull && docker compose up -d   # provision + migrate run before the new app starts
docker compose ps; docker compose logs --since 10m app
```
**AWS:** merge to `main`. The Release workflow snapshots RDS, migrates, rolls out with automatic rollback, and verifies, per account (staging → canary → rest).

**Rollback:** set the previous `HRMS_IMAGE` and run `docker compose up -d`, or redeploy the previous image tag on AWS. Migrations are forward-only and written to stay compatible with the previous release. If a release must be undone *with* its data changes, restore the pre-upgrade backup (section 10). `migrate --status` exits with `3` if the database is newer than the running image.

## 10. Backup and restore

**Compose**
```bash
bin/backup                         # ./backups/<project>-<timestamp>.dump + .sha256 (pg_dump custom format)
bin/restore ./backups/<file>.dump --confirm <COMPOSE_PROJECT_NAME>   # replaces this installation's data
```
Schedule `bin/backup` with cron, and copy backups **off the VM**, encrypted. Backups contain personal data.

**AWS:** RDS point-in-time recovery, AWS Backup (daily, 35 days) and pre-release snapshots. Restore to a **new** instance, then repoint. See [BACKUP_AND_RESTORE.md](BACKUP_AND_RESTORE.md).

## 11. Rotate credentials

- **DB role passwords (Compose):** put new values in `DB_OWNER_PASSWORD` / `DB_APP_PASSWORD` (`openssl rand -hex 24`), then run `docker compose up -d`. `provision` sets the new passwords before the app restarts. **AWS:** taint/replace the `random_password` resources, apply, then release.
- **Postgres superuser (Compose):** run `docker compose exec db psql -U postgres -c "ALTER ROLE postgres PASSWORD '<new>'"`, then update `.env`.
- **`DATA_ENCRYPTION_KEY`:** **do not change it.** Existing bank details would become unreadable. Re-encryption tooling doesn't exist yet.
- **User passwords:** each user, under My account → Change password. Admin recovery: section 5.
- **Biometric device keys:** Attendance setup → Devices → Rotate key.

## 12. Troubleshooting

| Symptom | Check |
|---|---|
| `app` exits at start with "Invalid deployment configuration" | The message lists each bad field. Common: unquoted colour in `.env` (`"#14532D"`), `APP_URL` not https, a `/branding/` file missing |
| `app` running but not healthy | Not bootstrapped yet (run bootstrap), or migrations pending (`docker compose logs migrate`) |
| `provision` / `migrate` failed | `docker compose logs provision migrate`. Wrong or missing secrets in `.env`; database not healthy |
| Browser shows "This address is not configured" | The hostname isn't in `APP_URL` / `APP_EXTRA_DOMAINS` |
| Login works but nothing loads | A forced password change is pending (the UI shows the form); or cookies are blocked because the site isn't served over HTTPS |
| Setup link says invalid | Already used or expired: run bootstrap with `--reset-admin` |
| Module missing in the UI | Not in `ENABLED_MODULES`, or not configured (Settings → Installation shows why) |
| Logs | `docker compose logs -f app` (JSON lines, one `reqId` per request; error responses show `Reference: <reqId>`). AWS: CloudWatch `/hrms/api`, `/hrms/ops` |
| Migration state | `docker compose run --rm migrate node dist/src/db/migrate.js --status` (0 = up to date, 2 = pending, 3 = database newer than image) |

## 13. Decommission a customer

**Compose:** export data if the contract requires it (`bin/backup`, plus any agreed export format). Then run `docker compose --profile https down` and **only when certain** `docker compose down -v`, which deletes the database volume permanently. Remove the directory. Keep or destroy backups according to the retention agreement.

**AWS:** follow infra/README.md "Offboarding": final snapshot, disable deletion protection, `terraform destroy`, close the account. KMS key deletion is a separate, guarded step.
